# Solution architecture

The contract says where the change lives and what it must honor. It should be specific enough that a
reviewer can point at a line of code and say whether it conforms. Write it into the work item under
"Architecture contract", using [references/architecture-contract.md](references/architecture-contract.md).
Change `docs/architecture.md` only when a lasting boundary changes.

## Dependency rule (S §3.1)

```text
Frameworks and infrastructure depend on application contracts.
Application contracts depend on the domain.
The domain depends on neither.
```

- **`domain`** holds validated identifiers and value objects, entities, state transitions and invariants,
  domain errors, and deterministic policies. It never holds framework extractors, SQL rows, HTTP status
  codes, environment access, global clocks or random sources, logging setup, or broker types (S §5.2).
- **`application`** holds use cases and the ports they need. Ports are shaped around use-case needs, not
  generic CRUD. Transaction requirements are explicit (S §5.3).
- **Adapters** implement ports, own technology types and errors, map external data to internal types,
  and set timeouts, retries, and telemetry at the boundary (S §5.4).
- **Composition roots** (one per binary) are the only code that knows every concrete technology. Startup
  order follows S §5.5. Diagnostics start before anything that can fail slowly, and nothing accepts
  traffic half-constructed.
- Start with few crates. Split at a real responsibility, dependency, compilation, or reuse boundary, and
  never merely to shorten files (K §10.2, S §5.1).

## Ports

- **Errors.** A port's error type is the application's own taxonomy, sorted by what the caller can do:
  validation, auth, not found or conflict, timeout, transient, permanent, exhausted, invariant
  (K §13.1). A public variant never wraps `sqlx::Error`, `reqwest::Error`, or any other technology error
  (S §5.3).
- **`Send` bounds are a decision, not an accident** (S §5.3). Record which one applies, and put it in
  an ADR the first time:

  | Need | Signature |
  |---|---|
  | Static dispatch, callers never spawn | bare `async fn` in the trait |
  | Static dispatch, futures spawned on a multi-threaded runtime (most services) | `fn op(&self, …) -> impl Future<Output = …> + Send`, or a `trait_variant` macro |
  | Runtime-selected implementation behind `dyn` | `async-trait`, or `Pin<Box<dyn Future + Send + '_>>`, costing one allocation per call |

- **Dispatch.** Prefer compile-time assembly with static dispatch. Use `dyn` only when runtime selection
  is a real requirement (S §3.2, K §11.3).
- **Contract tests.** When two adapters implement one port, a reusable contract test suite defines what
  "replaceable" means (S §20.2).

## Boundaries and data

- **Translate explicitly at every boundary.** The chains are: HTTP DTO → command → domain values; row ↔
  entity; external payload → integration model → application value. One struct never serves as row,
  entity, request, response, and message at once (S §20.3, §20.4).
- **Model invariants with types.** Use newtypes with private fields and validating constructors, enums
  for closed sets and state machines, and no boolean-heavy signatures (K §11.1).
- **Keep public API surface minimal** (K §11.4). Avoid exposing dependency types. Weigh
  `#[non_exhaustive]` against its compatibility tradeoff. Treat semver as a design constraint.
- **Schema change is expand-and-contract** (K §21.4). Plan the independently deployable steps as linked
  cards.

## Runtime behavior

- **Configuration** is read once at the composition root into validated typed settings, and passed down
  explicitly. Core crates never call `std::env::var` (S §3.3, §12). Use the one prefix and separator
  from brief §12.
- **Concurrency.** Start synchronous unless concurrency is required (K §14.1). Name the runtime
  boundary, the blocking-work strategy, cancellation safety, and supervision of spawned tasks (K §14.2).
- **Bounds.** Every queue, channel, request body, collection, recursion depth, decompression ratio, and
  parse time on untrusted input has a stated bound and an overload behavior (K §13.6, §22.2).
- **External calls** have a finite timeout, an end-to-end deadline, a retry policy for transient errors
  only with backoff and jitter, and idempotency before any retried side effect (K §13.5).
- **Observability.** Name the spans and fields, the metrics with low-cardinality labels, and the domain
  outcomes worth counting (K §24.2, S §13). Local development exports nothing by default.
- **Shutdown.** Stop intake, drain within a deadline, flush, cancel the rest, and exit meaningfully
  (K §24.3).

## Stack profiles (S §4, P §6)

Choose the smallest profile that meets the acceptance criteria. Adding a profile adds its obligations,
and those need answers before code:

| Profile | Adds | Obliges |
|---|---|---|
| `cli` | Domain and application crates, and a thin `apps/<name>` whose argument parsing is an adapter | Exit-code contract, stdout and stderr split, argument stability |
| `http` | `apps/server`, an HTTP adapter, `.env.example` | Health and readiness meaning, shutdown deadline, request and concurrency limits, `Send` ADR |
| `persistence` | A persistence adapter, `migrations/`, `compose.yaml`, `.sqlx/` | Brief §8 in full, a real local PostgreSQL (SQLite is not a substitute), and an integration-test strategy |
| `worker` | `apps/worker`, starting with a bounded in-process channel | Idempotency, retry, dead-letter, and shutdown policy |
| `full-local` | A Compose `full` profile, seed data, `tests/system/` | One command to start, one to clean up, and health-based startup |

Every profile addition, and every recipe it brings, is an ADR plus a same-commit update to the `justfile`
and `CONTRIBUTING.md`.

## Changeability check (S §20.5, §20.6)

Before a crate enters a core layer, answer five questions:

1. Is the type part of the business language?
2. Does it force a runtime, serialization, storage, or protocol choice?
3. What changes if the crate is replaced?
4. Is a small conversion at the boundary enough?
5. Is the abstraction cost greater than the realistic cost of replacing it?

Do not wrap every library, and do not claim portability no one needs (S §3.6).

## Test plan by layer (S §14.1)

Map every acceptance criterion to its cheapest meaningful layer:

- Domain unit tests.
- Application tests with fakes.
- Adapter integration tests against the real dependency.
- HTTP tests with an in-process router.
- System tests.
- Doc tests.

Add property or fuzz tests for parsers and state machines (K §17.4). Name what stays unverified, and the
stage that will verify it.
